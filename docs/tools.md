# Tools: what each agent can call, and how a tool call works

> Generated by `python -m app.tools_catalog` from the code that declares the tools -- don't edit by
> hand. `tests/test_tools_catalog.py` fails when this file is out of date.

## Who uses tools

| Agent | Model | When | Tools | Also |
|---|---|---|---|---|
| **The live tutor** | Gemini Live (native audio), in his browser | during the session | `next_step`, `end_session` | -- |
| **The memory agent** | the summary model chain | after each session | the memory tools below | -- the text the tutor reads is then assembled by code from the sections (`app/memory_text.py`, 16) |
| **The plan builder** | the summary model chain | after the memory update | the plan tools below | a names-game set when due (**structured output**: `CheckInProposal`) |
| **Research** (optional) | the summary model chain | inside the plan build | `research_technique` -> the research sub-agent's `web_search` | the findings (**structured output**: `ResearchFindings`) |

Structured output is used where the result is ONE whole object made at once (the memory text was
one until plan 16: a rewrite that dropped checked items, so it is now assembled by code). Tools are used where
the work is many small decisions that each need checking, on a document that persists (the memory)
or is built step by step (the plan): the model never rewrites the whole thing, so it can't silently
drop something; code applies each change, computes every number, and saves the document at the end.
There is no JSON Patch: the tools ARE the operations (add / replace / remove one item, record one
result, add one step).

## How a tool call works (the text agents: memory, plan, research)

The loop is ours, not the SDK's automatic function calling (`app/agent/runner.py`,
`run_tool_loop`), so every call is validated, logged and bounded:

1. **Declaration.** Each tool is a `Tool(name, description, parameters, handler)`. `parameters` is a
   JSON Schema: types, required fields, allowed values (`enum`), and a description per field (with
   its language: "HEBREW: ...", "ENGLISH: ..."). Plan tools are generated from the step classes in
   `app/steps.py` (`GUIDE` -> the description, the fields' descriptions -> the schema), next to the
   rules the tutor gets for that step -- one place, no drift.
2. **The request.** Every round sends the system prompt (the workflow: which tool when, in what
   order -- `prompts/*.yaml`), the context and the conversation so far, and `tools=[...]` (all the
   declarations). That list is how the model knows its tools and their parameters.
3. **The call.** The model answers with one or more function calls instead of text:
   `{"name": "update_memory", "args": {"section": "interests", "op": "add", "item": "..."}}`. The SDK
   gives us `args` as a plain dict (parsed JSON) -- not a Pydantic model.
4. **Validation and the handler.** The handler checks the dict (some build a Pydantic model from it,
   e.g. `ThreadStep(**args)`, `SessionSummary(**args)`; others check by hand: allowed values, length,
   duplicates, "copy the item exactly"), then applies it to a working copy (a `MemoryDraft` /
   `PlanDraft`) and returns a small dict, e.g. `{"ok": true, "next_due": "..."}` or the plan's running
   length at his pace.
5. **The reply.** The results go back to the model as function responses, and the loop runs again,
   until the model answers with plain text (it's done) or the round limit (memory:
   the `memory_max_tool_rounds` setting, plan: `PLAN_MAX_ROUNDS`, research: 3; web search: the
   `research_max_searches` setting + 2).
6. **Saving.** Only after the loop, code saves the documents (the memory, the plan, the needs, the
   session's results) -- never the model.

## Error handling

- **A bad call is not a crash.** A handler raises `ValueError` with the reason; the loop sends
  `{"error": "<reason>"}` back as that call's response, and the model fixes it in the next round
  ("this name isn't from his data -- choose another", "the plan is ~6 of 9 minutes: add more steps",
  "this time the task is retell"). An unknown tool name is reported the same way.
- **Rules the model can't skip** are enforced by code: `finish` refuses a short plan or one without
  the sequencing task due; a missing `record_sequencing` gets one extra round with only that tool;
  `update_profile` doesn't exist for an account with an uploaded profile.
- **The model service.** Every call goes through `app/llm.py` `generate()`: a fallback chain of models
  (overloaded / quota -> the next model at once; 500/502 -> retried with backoff; a model that failed
  "cools down" for 10 minutes), within one shared time budget per update (`_bounded_generate`).
- **When everything fails**, the session is marked (`memory_status` / `plan_status` = failed, with
  the error), and the hourly sweep retries it; the family can also press "process now" on the
  caregiver page. Research is optional: if it fails, the plan is built without it.

## Logging

- **Every tool call** is logged to the server log (Cloud Run): `[agent] update_memory({...}) -> ok`
  or `-> <the error>` (arguments shortened). A loop that hits its limit logs
  `[agent] stopped after N rounds`.
- **Per session**, the counts are saved: `memory_tool_calls`, `memory_tool_errors`,
  `plan_tool_calls`, `plan_tool_errors`, the model that answered (`memory_model`, `plan_model`) and
  the attempts.
- **The results** the tools produced are on the session and the caregiver page: the summary, word
  results, names game, sequencing score, needs, flags and tutor issues, the steps of the next plan.
- The archive keeps the exact prompt each live session got (the private bucket, 30 days).

## The live tutor's tools (different: in the browser)

- Declared once in `app/live_token.py` and locked into the session's token: the browser can't
  change them.
- The calls arrive at the page over the session's connection as JSON
  (`{"toolCall": {"functionCalls": [{"id", "name", "args"}]}}`); `static/app.js` (`handleToolCall`)
  answers with a `toolResponse`.
- `next_step` is **blocking**: she waits for the reply. The page enforces the session's rules before
  answering -- not after she asked a question in that turn, not before he answered enough times --
  and replies with the next step's text, or "not yet" and what to do. Held calls are saved with the
  session (`steps_held`) and shown on the caregiver page.
- `end_session` is **non-blocking**: she can finish her goodbye. Accepted only after he said goodbye
  (or after the silence notice); otherwise refused with the reason.
- Logging: the page's debug panel (`?debug=1`); what she reported per step (`steps_done`) and the held
  calls are saved with the session.

## 1. The live tutor

### `next_step`

*blocking*

Call when his answer has just finished the CURRENT STEP -- FIRST, before you say anything. Then, in ONE turn, react to what he said and continue with the step the reply gives you. Never ask a question of your own before calling it.

| Parameter | Type | Required | Allowed values | Description |
|---|---|---|---|---|
| `done` | string | yes |  | Which step you finished (English, a few words). |
| `how_it_went` | string |  |  | One short English sentence. |

### `end_session`

*NON_BLOCKING*

Hang up and end today's practice session. Like a goodbye between two people, BOTH sides must say goodbye first: call this only in the turn AFTER he has said goodbye back to you (or when he himself said goodbye / asked to stop). NEVER call it in the same turn as your own goodbye -- say goodbye, then wait for his reply.

_No parameters._
