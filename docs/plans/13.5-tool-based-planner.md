# Sub-plan 13.5: A plan builder that builds the plan with tools, step by step

Part of the [master design](00-master-design.md). After [13](13-session-agenda.md), before [14](14-sequencing-stories.md). Requested by Tomer (2026-10-12).

## Why
Today the plan builder (`app/agent/next_class.py`) makes **one** model call that returns the whole plan (`ClassPlan`) as structured output. Code then checks it after the fact:
- **It drops items:** names not in his data (8.5), the names game's untreated names (12), the closest family's names (13). If too little is left, it rejects the whole plan and retries once with a note.
- **The model never sees how long the plan will take.** In Tomer's sessions a fast talker got through the whole plan in ~4–5 minutes (13).
- **The order of the steps is fixed** by `app/agenda.py` (game → practice → activity → reserve → topics), whatever fits the day.
- **New kinds of steps** (sequencing in 14) mean a longer single prompt and a bigger schema.

## Goal
The plan builder builds the plan **step by step, with tools**:
- Each item is checked **when it's added**, and the builder fixes it on the spot.
- The builder chooses the **order** of the steps.
- It works to a **time budget** (~9 minutes at his pace), and can't finish before reaching it.

The result is the same `ClassPlan` (plus an order), so the session, the steps (13), the prompt and the caregiver page don't change.

## Design

### A. The tools (the same pattern as the memory agent: `runner.py` + a draft)
| Tool | What it adds | Checked on the spot (the reply says why when rejected) |
|---|---|---|
| `set_goal(type, description)` | The main goal | Rotation: not the same type 3 times in a row without a reason |
| `set_opening(recall, warmup)` | The greeting's recall line and warm-up | — |
| `place_names_game()` | Where the names game goes (its names are chosen at session start, 12) | Once; not first |
| `add_practice(name, topic, question, hints…, about_his_life)` | A practice name inside a topic (13) | In his data (8.5); not an untreated names-game name (12); not the closest family or his town (13); not a repeat |
| `add_activity(kind, instructions)` | An activity (discourse, high-level language…) | — |
| `add_games_activity(...)`, `add_game_homework(game_id, why)` | The games app (06) | Only games he has |
| `add_thread(topic, question)` | A conversation thread | — |
| `add_reserve_practice(...)`, `add_reserve_thread(...)` | The reserve (12b) | As for practice |
| `set_closing(homework, fatigue_fallback, avoid)` | The closing and the safety net | — |
| `finish(notes_applied)` | Done | Rejected while the plan is under the time budget, or has no goal |
| `research_technique(question)` | (Already a tool today, 07) | As today |

- **Every reply reports the running time:** "added; the plan is now ~6.5 of ~9 minutes at his pace". The estimates are plain code, from his pace (12b): the names game ~1.5 minutes; a practice name in a topic ~1–1.5 (more for a slow, long-answering pace); an activity ~2–3; a thread ~1–1.5.
- **The order is the order of the calls.** `app/agenda.py` follows it instead of its fixed order. The opening is always first; the reserve and the follow-up step always last.
- **Each tool's description explains how to build that step well.** For example `add_practice`: "a topic from his life, the name comes up inside it, a question that doesn't give the name away, hints in this order…". The instructions sit where they're used, instead of one long system prompt.

### B. Safety nets
- **A round limit** (as for the memory agent). If the loop fails or runs out, the previous plan stays, and the hourly sweep retries (as today).
- **The weaker fallback model:** if the loop fails on the smallest model, fall back to today's single-call builder (kept as the fallback path).
- **The plan's checks** (`enforce_plan_rules`) stay as a final check on the result.

### C. What doesn't change
- `ClassPlan` (with a new `step_order`), the names-game set (12), session start, the steps (13), the caregiver page's plan view.
- The research phase (07) becomes one of the tools in the same loop, instead of a separate phase before the plan.

## Files
| File | Purpose |
|---|---|
| `app/agent/plan_tools.py` (new) | The tools and the plan draft; the on-the-spot checks; the time estimates. |
| `app/agent/next_class.py` | Run the tool loop; fall back to the single call; save the plan as today. |
| `prompts/next_class.yaml` | A shorter system prompt for the loop (how to work, the priorities); the details go into the tools' descriptions. |
| `app/schemas.py`, `app/agenda.py` | `step_order` in the plan; the steps follow it. |
| `tests/` | Each tool's checks; the time budget (finish rejected under it); the order; the fallback; a fake builder run end to end. |

## Check before deploying
- **Build a plan for each account (dry run, nothing saved):** look at the order and the time estimate for a fast and a slow talker. Compare with today's builder: the number of model calls, the time it takes, the cost.

## Done when
- [ ] Plans are built with the tools, fit ~9 minutes at his pace, and the builder chooses the order.
- [ ] A rejected item is fixed on the spot (seen in the logs), not dropped after the fact.
- [ ] If the loop fails, the previous plan or the single-call builder takes over.
- [ ] `pytest` passes.
