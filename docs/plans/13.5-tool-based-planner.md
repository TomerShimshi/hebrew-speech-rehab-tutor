# Sub-plan 13.5: The plan is a list of steps, built by the plan builder with tools

Part of the [master design](00-master-design.md). After [13](13-session-agenda.md), before [14](14-sequencing-stories.md). Requested by Tomer (2026-10-12).

## Why
Today the plan builder (`app/agent/next_class.py`) makes **one** model call that returns the whole plan (`ClassPlan`, separate fields: `practice`, `activity`, `reserve_topics`…) as structured output. Then:
- **Code checks it after the fact.** It drops names not in his data (8.5), untreated names-game names (12), and the closest family's names (13). If too little is left, it rejects the whole plan and retries once.
- **The model never sees how long the plan will take.** A fast talker got through a whole plan in ~4–5 minutes (13).
- **A second layer, `app/agenda.py`, turns the fields into steps,** in a fixed order, each wrapped in a fixed template. So the same plan has two representations (TODAY'S PLAN and "the next session's steps"), and the generic templates are part of why sessions felt mechanical.
- **Two session modes to support:** steps mode (13) and the old one.

## Goal
1. **The plan IS an ordered list of steps,** and the session runs exactly those steps.
2. **The plan builder builds it with tools, step by step:**
   - each step is checked when it's added and fixed on the spot;
   - the builder chooses the order;
   - it works to a time budget (~9 minutes at his pace).
3. **Each step type is one class that owns its fixed rules,** so the lessons from the live tests can't drift.
4. **Steps mode is the only mode.** No toggle, no legacy plan path.

## Design

### A. Step types: one class each (content + fixed rules)
```python
class PracticeStep(Step):
    kind = "practice"
    # Fixed rules, written by us (the lessons of 12-13); the model never writes them.
    RULES = ("A short conversation about the topic; the name comes up inside it. Hints one at a "
             "time in this order ... After the name, one follow-up. Then the step is finished.")
    # Content, written by the plan builder through its tool.
    topic: str        # ENGLISH: "his years at work"
    name: str         # HEBREW: the target
    question: str     # HEBREW: asks for it without giving it away
    hints: Hints      # meaning / first syllable / sentence to complete
    bridge: str = ""  # HEBREW: a lead-in line that fits him
    about_his_life: bool = False

    def instruction(self) -> str:  # what the tutor gets as CURRENT STEP = content + RULES
        ...
```
- **Each class defines in one place:**
  - its content fields (with descriptions);
  - its `RULES` for the tutor;
  - its guide for the plan builder (how to fill it well);
  - its checks.
- **The plan builder's tool for each type is generated from the class:** `add_practice`'s parameters and description come from the fields, their descriptions and the guide.
- **Saved in Firestore** as a list of `{kind, …content}`. The rules aren't saved: they come from the code. So a rules change reaches every plan at once, with no rebuild.
- **The types (first round):**

  | Type | Content (from the builder) | Fixed rules (from the class) |
  |---|---|---|
  | `opening` | recall line, warm-up | greet, how he feels, react; ends after his answer and her reaction |
  | `names_game` | (none: a placeholder; the names come at session start, 12) | word for word, no hints, the name warmly on a miss, ends after the last question |
  | `practice` | topic, name, question, hints, bridge | a topic conversation, the name inside it, hints in order, one follow-up |
  | `activity` | kind, instructions, why | give it time, let him complete it |
  | `games_activity` | instructions | talking practice built on what he played |
  | `thread` | topic, question, follow-up ideas | at least one follow-up on his own words |
  | `reserve_practice`, `reserve_thread` | as practice / thread | used only if the main plan runs out (12b) |
- Sequencing (14) will be another class and tool.
- **The session-level parts stay in the plan,** outside the steps: the goal, homework, fatigue fallback, what to avoid, game homework, notes_applied.

### B. The plan builder's tools (the same loop as the memory agent: `runner.py` + a draft)
- `set_goal(type, description)`
- `add_<type>(...)` for each step type, in the order the builder wants them; `place_names_game()` once
- `set_closing(homework, fatigue_fallback, avoid)`, `add_game_homework(game_id, why)`
- `research_technique(question)` (today's research phase, 07, becomes a tool in the same loop)
- `finish(notes_applied)`

**Checks, with the reason in the reply when a step is rejected:**
- in his data (8.5);
- not an untreated names-game name (12);
- not the closest family or his town (13);
- not a repeat;
- games he has (06);
- goal rotation.

**The time budget:**
- every reply reports it, e.g. "added; the plan is now ~6.5 of ~9 minutes at his pace";
- the estimates are plain code, from his pace (12b): names game ~1.5 min, practice in a topic ~1–1.5, activity ~2–3, thread ~1–1.5;
- `finish` is rejected under the budget or without a goal.

### C. At session start (code: only what can't be known when the plan is built)
- Fill the `names_game` placeholder with the day's names from the set (rotation, 12).
- Remove today's game names from the practice steps.
- After the last step, the follow-up step; after 8 minutes, "you may close" (13).

`app/agenda.py`'s templates go away: each step's `instruction()` replaces them.

### D. One mode only (from plan 16, then numbered 15; moved here)
- **Steps mode for every account.** The "שיחה לפי שלבים" checkbox and `VoiceSettings.steps_mode` are removed.
- **No legacy paths:** the old TODAY'S PLAN rendering of practice / activity / reserve, the old `ClassPlan` fields, and the time-note-only flow without steps.
- **Before deploying:** a few of the patient's sessions in steps mode (one checkbox, before it's removed). Only Tomer has tested it so far, and the patient's pace is different (long answers).

### E. Safety nets
- **A round limit.** If the loop fails, the previous plan stays and the hourly sweep retries (as today).
- **A smaller fallback model that fails the loop:** retry on the next model in the list. If every model fails, the previous plan stays. (There's no single-call fallback any more: its plan format is gone.)
- **A final check on the whole plan:** a goal, at least the opening and one more step, under the round limit.

### F. Migration
- **No conversion:** after deploying, the latest plan of each account is rebuilt (the existing "rebuild" button, or a one-time script).
- **Sessions already saved** keep their old `class_plan` and `agenda` as they are, for history. The caregiver page shows them as before.

### G. Who reads the plan
- **The tutor:** the steps (A), plus the session-level parts in TODAY'S PLAN.
- **The memory agent:** the steps with their content, plus her `next_step` reports (13).
- **The caregiver page:** one list, "the next lesson" = its steps, with each step's content and the exact instruction she'll get.
- **The names game set (12):** unchanged.

## Progress (2026-10-12)
- **Built:**
  - `app/steps.py`: the step classes, each with its content fields, `RULES`, `GUIDE`, `MINUTES` and `instruction()`. `ProbeItem` moved here.
  - `app/agent/plan_tools.py`: the builder's tools, generated from the classes; the draft; the time budget.
  - `next_class.py`: runs the tool loop (16 rounds); the old after-the-fact rules and their retry are gone. Each practice step is checked by `practice_checker` when it's added.
  - `ClassPlan`: session-level parts + `steps` + `estimated_minutes`. The old fields are gone.
  - `class_plan.py`: `prepare_for_session` (fills the game, removes its names from practice, puts the opening first) and `session_steps`. `app/agenda.py` is removed.
  - One mode: `VoiceSettings.steps_mode`, the caregiver checkbox and the 2-minute names-game cue are removed; `next_step` is always declared.
  - Tutor prompt 2.0 (TODAY'S PLAN is session-level only; the names-game rules live in its step). Plan builder 0.16 (how to work with the tools; the details are in the tools). The intro plan is steps.
  - The caregiver page shows the plan in full (steps included) and its time estimate.
- **Changes from the design above:**
  - **Research stays a separate first phase,** as today, not a tool in the loop. It works, and it isn't what this round is about.
  - **No reserve kinds:** with a time budget the builder simply adds more steps; anything past ~9 minutes is used only if there is time.
  - **The closest-family rule is in the practice guide only,** not checked by code: code can't tell who in his data is close family.
- **Dry runs (nothing saved), both accounts:** each finished on the first try, 8–10 tool calls, 0 rejected.
  - Tomer: typical pace, 7 steps, ~10 minutes.
  - The patient: SLOW pace, 5 longer steps, ~9.8 minutes.
  - **Build time ~85 s** (vs ~20 s for the single call). That fits the end-of-session budget (300 s, shared with the memory update) and the sweep's (180 s).
- `pytest`: 260 passed (new: the step classes, the tools' checks and time budget, session start).
